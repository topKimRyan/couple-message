# 커플 우체통 메신저 기획서

Oct 4, 2026 · @김건우

## 개요

커플 우체통은 공부 때문에 자주 연락하기 어려운 커플이 가끔 안부를 남기고, 바뀐 연락처를 알리고, 졸업 후 다시 이어질 수 있게 해주는 웹앱이다. 실시간 채팅보다 몇 년 동안 꺼지지 않는 둘만의 우체통에 가깝다.

- **배경:** 고등학교 진학이나 입시로 연락이 끊기기 쉽고, 그 사이 전화번호나 SNS 계정이 바뀌면 다시 찾기 어렵다.
- **목표:** 기기, 전화번호, SNS 계정이 모두 바뀌어도 같은 방에 다시 들어올 수 있게 한다.
- **대상:** 운영자가 초대한 친한 커플만 사용한다. 공개 가입은 없다.

## 핵심 원칙

모든 설계는 "3년 넘게 손대지 않아도 그대로 돌아간다"를 최우선으로 한다.

1. **장기 유지:** 사용이 없어도 정지되지 않는 서비스, 만료되지 않는 주소를 쓴다.
2. **기기 독립:** 어떤 기기에서든 기억하는 정보만으로 로그인한다. 이전 기기, 전화번호, 이메일이 필요 없다.
3. **커플 간 분리:** 다른 커플의 방은 존재 여부조차 알 수 없다.
4. **운영자도 쉽게 못 읽음:** 이름, 생일 원본은 저장하지 않고 편지는 암호화해서 저장한다.
5. **초대제:** 운영자가 준 초대 코드가 있어야 방을 만들 수 있다.

## 사용자 흐름

방은 한 번만 만들고, 이후에는 둘 다 같은 다섯 가지 정보로 들어온다.

1. **초대:** 운영자가 커플에게 일회용 초대 코드를 전달한다.
2. **방 만들기:** 둘 중 한 명이 초대 코드와 다섯 가지 정보를 입력한다. 같은 정보로 방이 이미 있으면 만들지 않고 안내한다.
3. **상대 입장:** 상대방은 초대 코드 없이 다섯 가지 정보만 입력한다. 각자 "내 이름" 칸에 자기 이름을 쓰므로 시스템이 순서를 맞춰 같은 방으로 연결한다.
4. **홈 화면 추가:** 첫 입장 시 홈 화면에 추가하라는 안내를 띄운다. 아이폰은 이걸 해야 알림을 받을 수 있다.
5. **재로그인:** 기기를 바꾸거나 기록을 지워도 다섯 가지 정보만 다시 입력하면 된다.

## 로그인과 인증

로그인은 몇 년이 지나도 잊지 않는 다섯 가지 정보로만 한다. 비밀번호, 이메일, 전화번호는 받지 않는다.

| 입력 칸 | 입력 방식 | 처리 |
| --- | --- | --- |
| 내 이름 | 텍스트 | 공백 제거, 영문은 소문자로 통일 |
| 상대 이름 | 텍스트 | 공백 제거, 영문은 소문자로 통일 |
| 내 생일 | 달력 선택 | YYYY-MM-DD |
| 상대 생일 | 달력 선택 | YYYY-MM-DD |
| 사귄 날 | 달력 선택 | YYYY-MM-DD |

- **방 ID:** "이름+생일" 두 쌍을 정렬해 순서와 무관하게 만든 뒤, 사귄 날과 합쳐 해시한다. 둘이 각자 입력해도 같은 방 ID가 나온다.
- **본인 구분:** 정렬 전 "내 이름" 쪽이 어느 쌍인지로 보낸 사람을 구분한다.
- **느린 해시:** 해시를 일부러 느리게(PBKDF2, 수십만 회 반복) 계산해 무작위 대입을 어렵게 한다.
- **잠금:** 같은 기기나 IP에서 일정 횟수 이상 틀리면 잠시 잠근다. 틀린 정보는 다른 방 ID가 되므로 방 단위로는 셀 수 없다.
- **로그인 알림:** 새 기기에서 들어오면 상대에게 알림이 간다.

## 기능 명세

핵심 기능은 연락처 칸과 안부 편지 두 가지이고, 나머지는 있으면 좋은 기능이다.

| 기능 | 설명 | 우선순위 |
| --- | --- | --- |
| 최신 연락처 칸 | 방 맨 위에 고정. 각자 현재 번호, SNS 등을 적고 바뀔 때마다 고친다. 수정 시각 표시 | 필수 |
| 안부 편지 | 짧은 편지를 남기고, 열면 쌓인 편지를 시간순으로 본다. 읽음 표시 | 필수 |
| 새 편지 알림 | 웹 푸시로 새 편지, 연락처 변경, 새 기기 로그인을 알린다 | 필수 |
| 디데이 | 사귄 날로부터 며칠, 졸업까지 며칠 | 필수 |
| 방 삭제 | 운영자가 판단해 언제든 방을 삭제한다 | 필수 |

## 운영자 기능

운영자 화면은 초대 관리, 방 현황 확인, 방 삭제를 맡는다. 커플의 이름이나 편지 내용은 보이지 않는다.

- **초대 코드 발급:** 코드를 만들 때 "OO 커플"처럼 운영자만 보는 별칭을 붙인다. 방 ID는 해시라서 이 별칭이 없으면 어느 커플 방인지 알 수 없다.
- **방 현황:** 별칭, 만든 날, 마지막 편지 이후 지난 날수를 목록으로 본다. 오래 연락이 없는 방이 위로 오게 정렬한다.
- **방 삭제:** 운영자가 판단해 언제든 방을 삭제한다. 커플의 별도 동의는 받지 않는다.
- **접근:** 운영자 화면은 건우의 구글 계정 로그인으로만 연다.

## 기술 구성

집 서버 대신 Firebase에 올려서 이사나 컴퓨터 교체와 상관없이 같은 주소로 계속 접속되게 한다.

> (원문에 포함된 시스템 구성도는 [design.md](design.md#1-아키텍처)로 대체)

암호화와 복호화는 커플 기기에서만 일어나고, Firebase에는 해시 방 ID와 암호문만 저장된다. 서버 코드는 잠금 확인과 알림 전송만 맡는다.

- **웹앱(PWA):** 설치 없이 링크로 열고, 홈 화면에 추가하면 앱처럼 쓴다.
- **주소:** 갱신이 필요 없는 무료 기본 주소 `이름.web.app`을 쓴다.
- **계정:** Firebase 프로젝트는 건우의 구글 계정으로 운영한다.
- **무료 한도:** 커플 수십 쌍 규모면 무료 한도 안에서 충분할 것으로 예상한다. 정확한 한도는 개발 전에 확인한다.

## 데이터 저장과 보안

이름과 생일 원본은 어디에도 저장하지 않는다. 서버에는 해시값과 암호문만 남는다.

| 저장 위치 | 담는 것 | 누가 읽을 수 있나 |
| --- | --- | --- |
| invites/{코드} | 운영자용 별칭, 사용 여부, 사용 날짜 | 운영자 |
| rooms/{방 ID} | 만든 날, 사용한 초대 코드, 마지막 편지 시각, 두 사람 구분값, 암호화된 연락처 칸 | 방 ID를 아는 사람 |
| rooms/{방 ID}/letters | 보낸 쪽, 암호화된 편지, 보낸 시각, 읽은 시각 | 방 ID를 아는 사람 |
| rooms/{방 ID}/devices | 알림용 기기 토큰 | 서버만 |

- **암호화:** 다섯 가지 정보로 방 ID와는 다른 키를 하나 더 만들어 편지와 연락처를 AES-GCM으로 암호화한다. 복호화는 기기에서만 한다.
- **목록 차단:** 보안 규칙으로 방 목록 조회를 막는다. 방 ID를 정확히 알아야만 열린다.
- **한계:** 다섯 가지 정보를 모두 아는 사람은 들어올 수 있다. 운영자가 특정 커플의 정보를 알고 마음먹으면 풀 수 있으므로, 완전한 비밀 보장이 아니라 "쉽게 볼 수 없음" 수준임을 사용자에게 미리 알린다.

## 결정이 필요한 사항

개발 전에 남은 항목을 정해야 한다.

- [ ] **헤어졌을 때:** 운영자가 판단해 방을 삭제한다 (결정됨)
- [ ] **서버 코드 실행 방식:** 잠금과 알림 전송에는 서버 코드가 필요하다. Firebase Cloud Functions는 결제 수단을 등록하는 요금제가 필요한 것으로 알고 있어 확인이 필요하다. 무료로 가려면 이 부분만 Cloudflare Workers로 분리하는 방안도 있다.
- [ ] **공동 운영자:** 건우 계정에 문제가 생길 때를 대비해 믿을 수 있는 공동 운영자를 둘지
- [ ] **오래 안 쓰는 방:** 몇 년 동안 활동이 없어도 계속 보관할지, 기한을 둘지
- [ ] **서비스 이름과 주소:** 기억하기 쉬운 `이름.web.app` 주소

## 개발 로드맵

건우 커플이 먼저 쓰면서 검증한 뒤 친한 커플에게 연다.

1. **1단계, 뼈대:** Firebase 프로젝트 생성, 로그인 화면, 방 ID 계산, 방 만들기와 입장
2. **2단계, 핵심 기능:** 연락처 칸, 안부 편지, 암호화와 보안 규칙
3. **3단계, 알림과 앱화:** 홈 화면 추가(PWA), 웹 푸시, 새 기기 로그인 알림, 잠금
4. **4단계, 운영:** 초대 코드, 운영자 화면, 방 삭제
5. **5단계, 시범 사용:** 건우 커플이 직접 사용하며 수정
6. **6단계, 공개:** 친한 커플에게 초대 코드 배포
